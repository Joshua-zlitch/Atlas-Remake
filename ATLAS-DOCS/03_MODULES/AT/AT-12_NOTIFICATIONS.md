PURPOSE:

AT-12 provides notification capability for ATLAS.

It delivers important user-facing notifications generated by approved runtime
components, such as task completion, automation results, Guardian warnings,
permission-related information, and significant failures.

AT-12 owns notification creation, state, delivery coordination, and
notification lifecycle.

UX modules own notification presentation surfaces.

AT-12 does not own the UI itself.

NOTIFICATION MODEL:

Define a conceptual notification:

Notification
→ identity
→ title/summary
→ message
→ type/category
→ priority
→ source
→ timestamp
→ state
→ optional related task/automation/operation context

Do not define the final database schema.

PRIORITY:

Define conceptual priorities such as:

- INFO
- LOW
- NORMAL
- HIGH
- CRITICAL

Do not invent final enum values if implementation requirements later change.

The priority should determine appropriate presentation urgency.

CREATION:

Approved runtime modules may request notifications.

Examples:

AT-11 Automation
→ automation completed
→ AT-12

AT-07 Guardian
→ warning
→ AT-12

AI-07 Task Manager
→ task completed/failed
→ AT-12

AT-16 Permissions
→ user action required where appropriate
→ AT-12

AT-12 should not create notifications merely because every internal event
occurred.

Only meaningful user-facing events should generate notifications.

DELIVERY:

AT-12 coordinates delivery to approved presentation mechanisms.

Possible delivery targets include:

- In-app notification surface
- Desktop notification where supported

Do not assume a specific Windows notification API until implementation.

UX-04 presents notification information within the application.

UX-03 may visualize relevant notification state.

AT-12 owns delivery state, not UI rendering.

LIFECYCLE:

Define conceptual states:

- CREATED
- QUEUED
- DELIVERED
- READ
- DISMISSED
- EXPIRED
- FAILED

A notification must not be reported as delivered if delivery failed.

READ/UNREAD:

Notifications may maintain read/unread state.

User interaction with the notification UI should update the state through
approved interfaces.

DISMISSAL:

Users may dismiss notifications.

Dismissal should not automatically delete underlying task/automation state.

PERSISTENCE:

Important notification history may persist locally where appropriate.

Do not persist every transient notification indefinitely.

SQLite may be used as the local persistence layer.

Do not invent a final schema.

AUTOMATION:

AT-11 may request notifications for automation outcomes.

AT-12 owns delivery.

GUARDIAN:

AT-07 may generate warnings.

AT-12 may deliver those warnings.

AT-12 does not evaluate the underlying condition.

TASKS:

AI-07 Task Manager may request notifications for important task state
changes.

AI-08 verification results may be included when relevant.

PERMISSIONS:

AT-16 owns permission decisions.

AT-12 may notify the user that a permission decision is required or was
denied.

AT-12 must not grant or deny permission.

IPC:

Renderer
→ IPC
→ runtime
→ AT-12

The renderer must not directly manage notification persistence or OS
notification APIs.

EVENT RUNTIME:

AT-17 provides event coordination.

AT-12 may consume relevant events and emit notification lifecycle events.

Do not implement a second event bus.

SECURITY:

Protect against:

- Notification spoofing
- Sensitive-data leakage
- Malicious notification content
- Untrusted AI-generated notification messages
- Excessive notification spam

Notification content should be treated as untrusted data and safely
presented.

PRIVACY:

Avoid placing sensitive information in desktop notifications when a less
revealing summary is sufficient.

Do not expose private file contents, credentials, or secrets through
notifications.

PERFORMANCE:

Notification delivery must not block the application.

Avoid generating excessive notifications from high-frequency runtime events.

Use aggregation/debouncing where appropriate.

ERROR HANDLING:

Cover:

- Delivery failure
- Invalid notification
- Persistence failure
- Unsupported notification target
- Permission-related notification failure
- Notification overload

A notification delivery failure must not be confused with the failure of the
underlying task that generated it.

ACCEPTANCE CRITERIA:

AT-12 is complete when:

- Approved runtime components can create notifications.
- Notifications have clear lifecycle state.
- Important notifications can persist where appropriate.
- In-app notification presentation works through the UX layer.
- Desktop delivery works where supported.
- Sensitive information is not unnecessarily exposed.
- Notification failures do not alter the underlying operation result.
- Notification spam is reasonably controlled.
- Relevant tests pass.
- Git diff is reviewed.
- Implementation is committed according to the ATLAS Git workflow.
